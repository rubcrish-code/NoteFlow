# Windows release checklist

Use an isolated Windows QA account or VM. Never run destructive installer tests against the maintainer's NoteFlow profile.

**1.0.0-rc.5 status:** RC5 functional smoke is accepted by the user. Second-PC installer lifecycle and NSIS/MSI coexistence were accepted for a previous RC; the newly rebuilt rc.5 installers have not passed a separate clean-install/upgrade/uninstall matrix. See `../tasks/rc5-usability-editor-polish-report.md` for functional evidence and `../tasks/rc3-full-regression-report.md` for previous installer evidence. This remains an unsigned prerelease, not final public v1. Before final 1.0, retain detailed lifecycle coverage, backups, signing and Windows 10 validation where support is claimed. The second-PC checklist is `rc-second-pc-smoke.md`; do not infer unreported platform results.

WiX cannot use the alphanumeric app prerelease as an MSI `ProductVersion`. For this RC, Tauri `version` / dynamic About is `1.0.0-rc.5`, while `bundle.windows.wix.version` is deliberately `0.99.5`. Ordering is rc.1 = 0.99.1 < rc.2 = 0.99.2 < rc.3 = 0.99.3 < rc.4 = 0.99.4 < rc.5 = 0.99.5 < final 1.0.0. Keep UpgradeCode `ff9d3de5-b119-5cb0-9873-43e30a097afa`. Do not use a fourth numeric field for upgrade comparisons. Verify both actual MSI locales after bundling.

1. **Preflight:** clean Git tree at the intended commit; matching package, lock, Cargo, Tauri and About versions; supported x64 Windows build; adequate disk space; record WebView2 version. Confirm the legal publisher and signing certificate before public distribution.
2. **Build:** run `scripts/release-windows.ps1` in PowerShell when its completely-clean-tree precondition is satisfied. For an explicitly approved pre-commit release tree with intentional local reports, run the same gates directly without weakening the script, then use `scripts/stage-windows-artifacts.ps1`. Also run `npm audit --omit=dev --offline=false` and its JSON form online: any production vulnerability stops publication. Verify isolated FTS, executable, English/Russian MSI, bilingual NSIS and `SHA256SUMS.txt` in Git-ignored `releases/windows/<version>/`. Publish the three installers and checksum file; keep standalone EXE local for QA.
3. **Package audit:** inspect ProductName, identifier, architecture, icons, installer language, Start Menu, Add/Remove Programs, install location, WebView2 bootstrapper policy, Authenticode status, and exact SHA-256 hashes. The standalone EXE is a QA artifact, not a replacement for an installer.
4. **Clean install (QA account/VM):** install NSIS and MSI in separate clean snapshots. Check first run, note/project/tag creation, editor, attachment/image, settings, close/restart persistence, offline core, and no console/debug UI. Test Windows 10 and 11 separately.
5. **Upgrade/reinstall (QA account/VM):** prepare a previous-version installation with notes, Markdown, checklist, project, tags, archive, assets, revisions, FTS, model metadata, chat history and external backup. Upgrade, then reinstall the same version. Verify data, search, settings and secure credentials remain. Close the app before either installer; test the installer-running-app prompt.
6. **Uninstall/reinstall (QA account/VM):** uninstall without selecting the NSIS data-deletion option. Verify binaries, shortcuts and Add/Remove Programs entry disappear while app data remains; reinstall and reopen it. Separately document what the optional data-deletion checkbox does. Never exercise it on a real profile.
7. **Disaster recovery (QA account/VM):** restore an external backup into a fresh isolated profile. Restart and verify notes, projects, tags, archive, managed assets, revisions, settings and AI/RAG history/sources. Confirm API keys are absent from the archive and re-enter credentials through secure storage.
8. **Failure gates:** test failed migration rollback and interrupted restore with temporary fixtures; verify a second launch focuses the existing window; verify autosaved content after forced close only in QA; launch from Start Menu and a different working directory. Record any untested scenario as NOT RUN, not as a pass. These lifecycle gates are deferred for the closed RC only and block final public v1 until validated.
9. **Sign and public release:** configure the real publisher certificate so the application EXE is signed before it is packaged; then sign MSI and NSIS, timestamp and verify all signatures. Restage the final signed binaries with `scripts/stage-windows-artifacts.ps1` so `SHA256SUMS.txt` matches the bytes to be published. Only then approve public v1. The current RC is explicitly **UNSIGNED**; SmartScreen warnings are possible. Do not change Windows security settings or imply a signature exists.
